Notes de performance — volumes attendus
  • Trucks (~200) et Employees (~250) : pas de pagination. Charger la liste complète en une requête — les réponses restent petites.
  • Trips (~1M/mois), Documents et Maintenances (millions) : pagination curseur obligatoire. Utiliser after (id du dernier item) + limit — évite le OFFSET SQL qui dégrade linéairement. Exemple : GET /trips?after=<cursor>&limit=50 → réponse inclut next_cursor et has_more.
  • Recherche + curseur : le curseur est lié aux filtres actifs. Tout changement de filtre remet le curseur à null (première page). Le curseur doit être traité comme opaque côté frontend.
  • Recherche par plaque (texte libre) : LIKE 'GN-%' avec préfixe fonctionne avec un index btree standard. Si la recherche doit être arbitraire (sous-chaîne), activer l'extension pg_trgm et créer un index GIN sur plate_number.

Composants UI à construire 1 composant
DataTable.svelte frontend/src/lib/components/common/
Composant table réutilisable unique pour toutes les vues liste de l'application. Gère l'état des filtres, le curseur de pagination, le chargement et les erreurs. Chaque vue passe uniquement sa config (colonnes, endpoint, filtres) — aucune logique de fetch ou de pagination dupliquée.
DT-024
  • Le composant est headless côté logique mais stylé avec le design system existant (styles .tbl-wrap, .chip, th/td du mockup)
  • Prop paginated (boolean) : false pour Trucks et Employees (charge tout en une requête, pas de contrôles next/prev) — true pour Trips, Documents, Maintenances (curseur + has_more)
  • Prop columns : tableau de { key, label, render? } — la fonction render optionnelle reçoit la valeur et la ligne entière, permet d'injecter badges, pills d'expiration, formatage de taille fichier sans que le composant connaisse le domaine
  • Prop filters : tableau de { key, label, value } pour les chips de filtre — le composant remet le curseur à null à chaque changement de filtre
  • Prop searchParam : nom du query param auquel l'input de recherche est mappé (ex. truck_plate, search)
  • États internes gérés : filtres actifs, curseur courant, données, loading, erreur — exposés via des slots nommés pour les états vides et d'erreur personnalisables
  • Doit être construit avant les vues Flotte, Trajets, Employés, Documents, Maintenances — toutes en dépendent
